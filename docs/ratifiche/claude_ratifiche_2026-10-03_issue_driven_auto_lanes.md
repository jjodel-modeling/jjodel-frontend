## 0. In brief

A nightly scheduled task picks GitHub issues that Alfonso labelled `auto`, runs each one as an orchestrated lane on its own `auto/` branch, and stops at the first sign of critical work or when the night's share of the plan window is spent. Nothing reaches the trunk without a merge decided as today. Until Alfonso switches it to live, the task runs in shadow mode: Phase 1 discovery only, so the first week measures how many issues are really automatable and what one costs.

## 3. Decisions

A second agent reviewed the first draft of this memo, the registry rows and the prompt (RC-27). It raised 19 objections on contradictions, injection paths, budget edge cases and implementability, and all of them are adopted below. Verified: the intake, guard and budget rules were checked against an attacker who edits a labelled issue and against a week already filled by daytime work; a reading that crosses `resetsAt`, or an issue edited after its label, would falsify them if admitted.

Terms. A night is identified as `night-YYYY-MM-DD`, the date on which it starts. The plan window is the seven-day window of the `rate_limit_event` readings, identified by its `resetsAt`.

**RC-35. Intake gate: a label applied by an allowlisted maintainer.** An issue enters only with the label `auto`, and the script checks through the issue events API that the actor of the latest `labeled auto` event is in an allowlist (initially `apierantonio`). The repository is public: anyone can open an issue, and its text would reach a session running under `bypassPermissions` on Alfonso's Mac. So the following are refused or parked. A title or body edited after that label event is refused until Alfonso labels the issue again. Hidden content (HTML comments, zero-width characters, bidirectional controls) is parked, because the GitHub page does not show it. Pull requests returned by the issues API are dropped. Comments are never read. The title and body are untrusted data. They are rendered into the discovery prompt inside a fence one backtick longer than the longest backtick run in the text, capped in length with the cut stated, and the template tells the lane to analyse that text as a bug report and never follow instructions in it. The branch slug is derived from the title but must match `[a-z0-9-]{1,40}`, and every value reaches a command as an argument, never through string interpolation. A skip label (`needs-alfonso`, `auto-parked`) wins while it is present. An attempt is keyed on the id of the `labeled` event, so one label gives one attempt, and labelling the issue again allows a new one.

**RC-36. The critical zone stays shut for automatic lanes, on three layers.** First, before Phase 2: the DOVE predicted by the discovery report is checked mechanically against the guarded paths, and a hit parks the issue. Second, during the session: automatic lanes start with `lane-run start --auto`, which refuses `--critical-zone-goahead` (so the hook denies under bypass), starts the session without GitHub credentials (`GH_TOKEN` and `GITHUB_TOKEN` removed, `GH_CONFIG_DIR` pointing to an empty folder), disallows the web tools, and marks the lane folder as automatic; the existing hooks already deny `git push`. The ledger flags any automatic lane folder that holds a `goahead.txt`. RC-30 stays available for lanes that Alfonso or a chat launches. Third, after the session: a diff guard compares the branch with the base sha recorded when the worktree was cut, and also inspects untracked and ignored files (`git status --ignored`). The guarded paths are `CRITICAL_FILES` of `frontend/scripts/hooks/critical-zone.mjs`, the D-layer creators of CLAUDE.md 3.2 in added lines (the hook's patterns), the governance files (`CLAUDE.md`, `AGENTS.md`, `docs/PROTOCOL.md`), everything under `.claude/` and `.github/`, `frontend/scripts/hooks/`, `lane-run.mjs` and the `auto-intake` files, `VersionFixer.tsx`, `package.json` and the lockfile, deleted files, and removed or changed `export` lines. The export check is a heuristic, and the report says so. A parked branch is kept, never deleted and never merged.

**RC-37. Output stays off the trunk.** Each issue runs on branch `auto/<issue>-<slug>` in worktree `~/jjodel-a-<issue>`, cut from the trunk tip, whose sha is recorded as the guard's base. The automation never merges and never pushes. A merge is decided as today: Alfonso's batch decision, or a chat merge after the visual check of RC-23 with the `pre-` tag of RC-31. GitHub writes: none in shadow mode. In live mode the automation writes labels only (`auto-ready`, `auto-parked`) and never comments, since comments would appear under Alfonso's account on collaborators' issues. Reporting goes to the owner chat as a morning digest plus one push line.

**RC-38. Budget: the night uses slack, never the margin.** Before every lane the script reads the latest `rate_limit_event` across the lane logs and admits a lane only when all of the following hold. (1) Pace: the seven-day utilization is at or below the elapsed fraction of the window, computed from `resetsAt`, minus 0.05. (2) Ceiling: utilization is below 0.70 in absolute terms, and the window does not reset within the next 24 hours, because daytime work concentrates at the end of the week (the previous week reached 0.99). (3) Nightly delta: the night stops admitting once utilization has risen 0.03 above its baseline, which is about 21 points over seven nights, the 20% share discussed in chat; `admit` writes the baseline to `baseline.json` from the first fresh reading of the night. (4) Time: 240 minutes of cumulative lane time per night, where parallel lanes add up; a lane is admitted only with at least 30 minutes left; a running lane finishes within its 90-minute limit, so the worst overrun is 90 minutes times the parallel lanes, capped at 2, and a second lane starts only after the first has produced a reading. (5) Kill switch: a `rejected` status, a five-hour utilization at or above 0.80, or a `surpassedThreshold` on the seven-day window ends the night, writes a trip file, and nothing is retried. A reading is stale when it is older than six hours or when its `resetsAt` has passed; a stale reading admits only one light discovery lane, whose own events refresh the reading. The ledger records time, `total_cost_usd` and tokens for every automatic lane, but admission does not use cost, because the plan window is the real constraint and is measured directly. The orchestrating chat's own usage is not in the lane logs; the script does the mechanics, the driver waits with `lane-run wait` and does not poll otherwise, and the first week measures its share from the nightly delta. All numbers here are provisional: under RC-26 they belong to Alfonso, and the shadow week calibrates them.

**RC-39. Shadow mode first.** Mode `shadow` is the default and stays until Alfonso switches to `live`, which will not happen before the MODELS demo (RC-26: nothing changes what the demo shows). The script refuses `live` unless the configuration records who ratified the budget numbers and when. In shadow mode the night runs Phase 1 discovery only, on the light tier, read-only, and each report ends with an eligibility verdict (`auto-eligible`, `needs-design`, `critical`) and the predicted DOVE on a machine-readable line; the digest lists verdicts, time and cost. Rendered prompts declare `Lane: full`, since Phase 1 ends in a hard stop. Live mode adds Phase 2 in cascade (the same session, per RC-20) for issues that are `auto-eligible` and pass the first layer of RC-36; a resume keeps the session's model, so the tier of Phase 2 is the tier chosen at start by `tierRule`, heavy when in doubt.

## 4. Mechanism

The deterministic parts live in one script, `frontend/scripts/auto-intake.mjs`, built by lane P-2026-10-03-1705: the intake gate, the rendering of the discovery prompt from `frontend/scripts/lane-templates/issue-discovery.md`, admission, the diff guard and the ledger. Its configuration (allowlist, labels, window, budgets, mode) sits in a JSON file beside it. `lane-run.mjs` gains only the `--auto` option of RC-36. The nightly driver is a Cowork scheduled task that requires the Mac and acts as the owner chat: it calls `auto-intake` and `lane-run` through osascript, reads reports from the repo, applies RC-36 and RC-38, and writes the digest. If the Mac is asleep or the desktop app is closed, the night is skipped. The scheduled task is created only after the script is merged.
